# Verify prompt — v1

**This file documents a node that deliberately does not call a model.**

Spec §7 puts `verify` between `propose_resolution` and `route`, asking two questions:

> - does the arithmetic close to the paise?
> - do cited precedents actually apply?

Both are answered in code, in `graph/nodes.py::verify`. The prompt file exists so the
decision is recorded where a reader looking for `prompts/verify/v1.md` will find it, rather
than being an unexplained absence.

## Why no model call

**A check performed by the model being checked is not a check.** The proposal comes from a
model reasoning about arithmetic; asking the same model, in the same session, whether that
arithmetic is right samples the same distribution that produced the error. It will agree with
itself far more often than it is correct — and the failure it is least likely to catch is
exactly the confident, plausible, wrong answer that `verify` exists to stop.

The arithmetic is computable, so computing it is strictly better than asking:

- `domain.money` already holds the paise-exact operations, including the net-vs-gross
  distinction (FR-2.8) that the case renderer got wrong once. The verifier reuses them, so the
  agent, the deterministic matcher and the verifier cannot drift apart.
- Whether a cited precedent applies is checkable structurally: it must have been retrieved
  (not invented), and its reason code must agree with the one being proposed. A precedent
  cited for a conclusion it does not support is a real defect, and it is detectable without
  judgement.

This costs one model call per case rather than two, which matters under the provider quotas
this project ran into (FAILURES.md) — but that is a side benefit, not the reason.

## What it cannot catch

Stated plainly, because a deterministic verifier invites more trust than it has earned:

- It confirms the arithmetic **closes**, not that the closure means what the proposal says it
  means. Two payments netting to a credit is consistent with a netted settlement and also with
  a coincidence; the verifier cannot distinguish those.
- Structural precedent checking cannot tell a genuinely apposite precedent from one that
  shares a reason code by accident. Ring 3's precedent precision, judged case by case, is what
  measures that properly.

Where a future version does need a model here — judging whether a rationale actually follows
from the evidence — it belongs in a **separate** call with its own prompt and no sight of the
proposer's reasoning, and it should be measured against hand-scored items before being
trusted. That is Ragas faithfulness, in spec §6, and it is Ring 4's work rather than Ring 2's.
